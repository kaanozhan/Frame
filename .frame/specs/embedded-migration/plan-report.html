1 · What & why

Frame used to write its meta files into the project root — AGENTS.md, tasks.json, STRUCTURE.json, PROJECT_NOTES.md, QUICKSTART.md, plus a CLAUDE.md → AGENTS.md symlink it planted after consuming the user's real file. The overlay release moved everything under .frame/ and reads nothing else. Projects initialised by the old version were left behind: their data sits a directory away from where Frame now looks, so Tasks, Structure Map and Overview come up empty.

The sharper problem is not the empty panels. contextPreamble.js:104 tells every Claude Code session “This repository's CLAUDE.md is yours to read as usual — Frame has not modified it” — while pointing at a symlink Frame itself planted, aimed at a generated AGENTS.md that describes the old layout. So an unmigrated project hands the agent two contradictory instruction sets, one lying about its own provenance, on every launch. That is what rules out the conservative-looking option of leaving the old files in place with a warning: leaving them is the broken state, not the safe one.

This plan builds an automatic mover. It runs without a prompt, sweeps every project in the workspace registry at startup rather than waiting for each to be opened, moves what Frame created into .frame/, hands back what Frame consumed, backs up everything it removes, and tells the user once what happened — without advising them how to run their repository.

Architectural notes
  • Why a sweep and not a per-open hook: Frame registers a list of projects while the renderer holds one currentProjectPath. Hanging migration off the switch alone would migrate five legacy projects across five sessions, each with its own notice, leaving unopened ones broken meanwhile.
  • The per-open path is not deleted, it is promoted to the foreground. It stays the route for projects added later — and it needs no stored failure state to know it is the recovery case: if the sweep had succeeded, the project would no longer be legacy. Every lazy firing therefore means the user is waiting on that project, which is what earns the modal. An in-flight guard stops it re-entering a project the sweep is still working on.
  • Never blocks startup. The sweep runs after the window is up. A failure in one project is caught and does not stop the rest.
  • The registry is the boundary of responsibility. Projects not in workspaces.json are not migrated and the disk is not scanned for them — leaving the registry means the user removed the project.

Architectural notes
  • Dual layout is the normal case. Pre-overlay init already wrote .frame/ — config.json, specs/, docs/, bin/. So migration adds files to a directory the repo already tracks or ignores, carrying no new git decision — and it can collide with post-upgrade work, which is why the counterpart check exists.
  • config.json.files is read before it is rewritten. The legacy config records exactly which root files Frame created for that project — a per-project manifest, stronger than matching well-known names. Anything unrecognised is reported, never moved.
  • Backup first, whole. Written before anything moves, so an interrupted run leaves duplicates the next pass reconciles rather than a hole. One directory per project, never overwritten, never pruned.
  • Deferral is deliberate, and deliberately silent. It guards a user mid-edit from having their work relocated under them — not from data loss, since the content moves intact either way.

Architectural notes
  • The git sentence keys off the deleted files, not the sharing mode. These diverge: a user who gitignored .frame/ but committed the root files derives local while the deletions are plainly visible. Conditioning on the mode would have stayed silent in exactly the case that needs explaining.
  • Restoration is the overlay rule's one sanctioned exception. It writes outside .frame/ — but only to return bytes this tool took, to the path it took them from, and only when nothing is there. An existing user file is never overwritten.
  • .claude/CLAUDE.md was copied, never unlinked. Verified against main's init: it is read into the merge and then breaks, with no unlink. It is left alone and never recreated.
  • The receipt reports; it does not advise. No “you should commit this”, no sharing-mode nudge. Its job is to answer why does my working tree have seven deletions before the user asks — attribution, not instruction.

Architectural notes
  • The engine does not know it is in the foreground. migrateProject takes an optional onProgress; the sweep passes nothing and the modal passes one that forwards over MIGRATION_PROGRESS. That is the entire difference between the two callers.
  • Deferral is silent in the sweep and explained here. Not an inconsistency: in the sweep nobody is blocked and there is nothing to do, while here the user has just selected the project and there is a concrete action — commit or stash the named files.
  • No “remove and re-add”. It would drop the workspaces.json entry and re-run identical code against identical files. What the screen offers instead is the actual error, the backup location, and a retry.
  • Untested by design. The testing record lists src/renderer/ as not covered — no DOM harness is installed. The engine behaviour behind every state here is covered by steps 3–6.

3 · Decision story

Business decisions

D1 · What triggers migration in a multi-project workspace?
chosen
Startup sweep over the registry, per-open kept as fallback
Every known project is usable from the first launch; costs an in-flight guard and per-project failure isolation.
Per-open trigger only
Simplest wiring — one call site — but migrates one project per session and leaves the rest broken.
Why: Frame registers a list of projects while the renderer holds a single currentProjectPath. A per-open trigger would have spread migration of five legacy projects across five sessions with five separate notices, and any project the user did not happen to open would keep feeding its agent contradictory instructions.
D2 · What about projects Frame no longer lists? follows from D1
chosen
Migrate when the user adds them back
No extra machinery; an old project is fixed the moment it re-enters the registry.
Scan the filesystem for stray .frame/
Catches forgotten projects, but has no defensible starting root, is slow, and writes to repositories Frame was never pointed at.
Why: workspaces.json is the definition of the set Frame is responsible for, and the only way out of it is the user removing a project — an explicit “stop tracking this”. Treating a de-registered project as still Frame's to modify would invert that.
D3 · What does the receipt report? follows from D1
chosen
One message per sweep; failures named, D4 deferrals omitted
Quiet and actionable; a deferred project is invisible until it resolves itself.
Report migrated, deferred and failed alike
Full transparency, but “X was deferred because you have uncommitted changes” recurs every startup with no action attached.
Why: With migration silent (D1) and the legacy banner removed (D10), a failed project has no other way to explain itself — so failures are named. A deferral is normal, self-resolving the moment the user commits, and reporting it teaches the user to dismiss the notice unread.
D4 · Does the bundled sample project stay in this spec?
chosen
Keep it, as its own sequencing step
Owns success criterion S10 inside this spec; adds src/templates/** to the footprint.
Split into a separate task
Keeps the footprint pure, but makes S10 unverifiable here and depends on other work landing.
Why: src/templates/sample-project/ ships root AGENTS.md, CLAUDE.md, tasks.json and companions, so detection matches the very first project a new user opens. It shares no code with the engine, but a separate spec ceremony for a template rewrite costs more than the rewrite.
D5 · What happens when the user selects a project that still needs migrating? follows from D1
chosen
A foreground modal with per-artifact progress
Gives a failed sweep a recovery path and explains the pause; costs a renderer surface that cannot be tested here.
Stay silent, as the sweep does
One code path and no UI work, but a project the sweep could not migrate opens broken with nothing to act on.
Why: The sweep is silent because nobody is waiting on it; the lazy path is the opposite. It also needs no stored failure flag to identify itself — a successful sweep would have left the project non-legacy, so any lazy firing is either a newly added project or one the sweep could not finish. Both mean the user just selected it and is waiting, which is when blocking UI is earned. A deferral is explained here even though it stays silent in the sweep, because here the user is blocked and there is a concrete action.
D6 · What does the modal offer when migration fails again? follows from D5
chosen
The real error, the backup path, and Try again
Every element is actionable; relies on the user fixing the underlying cause outside Frame.
Also suggest removing and re-adding the project
Gives the user one more thing to try, but it re-runs identical code against identical files and “remove” reads as data loss.
Why: Raised as a suggestion and argued down. Removing drops the workspaces.json entry and nothing else; none of the plausible causes — permission denied, a locked file, an unremovable symlink, a full disk — travel through the registry, so the round trip cannot work. What does help is naming the actual error, and the one sentence that stops the panic: nothing was lost, a copy of everything removed is in .frame/migration-backup/.

Technical decisions

D7 · How much of this ships with tests?
chosen
Everything the infrastructure can reach
Every disposition, deferral, restoration and interruption verified against real temp repos; the renderer receipt stays untested.
Pure logic only
Less test code, but leaves the irreversible part — deletion and moving — unverified.
Why: The testing record shows node --test test/*.test.js covering src/main/ and src/shared/, with gitExclude.test.js (12 cases) and gitSharing.test.js (24 cases) already exercising real temp repos — exactly this shape of work. src/renderer/ is recorded as Not covered: no DOM harness is installed, so the receipt is not testable here without first choosing one.
D8 · Where does the engine live, and what may it require?
chosen
One Electron-free module; paths injected, IPC done by the caller
Fully testable without stubbing Electron; index.js keeps two responsibilities (supply the registry, send the receipt).
init(window) like the other main modules
Conventional wiring, but pulls Electron into the one module whose correctness matters most.
Why: The same injection convention globalLayer follows — init(userDataPath) rather than requiring Electron — kept that module and its tests Electron-free. gitSharing.js and gitExclude.js are the same shape. This is the module where the project's own testing convention pays off most.
D9 · Which surface renders the receipt? follows from D3
chosen
Extend healthNotice.js with a neutral kind and one action
~25 lines on a 90-line file that already owns app-level messages pushed from main; needs a non-alarming variant added.
A dedicated popover module
Comfortable with multi-line text and actions, but duplicates a dismissal lifecycle for a single message.
Why: notify.js auto-dismisses in 2–4 s and takes no action button — too ephemeral for a receipt the user must actually read. A bespoke popover would repeat the pattern whose last instance (sharingHint) was reverted in d47f337, and notify.js's own header argues against per-surface copies. healthNotice gains an info kind (role="status", information icon) because a completed migration is not a degraded state.
D10 · frameProject.js is flagged IN-FLIGHT — coordinate or proceed?
chosen
Proceed; the flag is stale
No waiting; relies on the reading of another spec's outcome being correct.
Sequence after that spec closes
Zero collision risk, but blocks on a spec whose remaining work cannot touch these files.
Why: spec-context.js reports src/main/frameProject.js inside audit-q3-performance-resources (phase implementing). That spec's outcome.md records T01–T10 captured, with only T10 pending as “static done, runtime pending” — a measurement pass touching neither frameProject.js nor index.js. Both edits here are a few lines in distinct regions.

A non-git project has no dirty-check before its files moveAccepted deliberately: the failure mode D4 guards against needs a git diff to exist. The backup is the recovery path; an mtime guard would strand actively-edited projects permanently.
A migration fails and nobody noticesNamed in the receipt, recorded step-by-step in the activity log, and reported by the one telemetry event. Step 1, then step 7.
A failed project is opened and there is nothing the user can do about itThe foreground modal retries it with visible progress and, on a second failure, shows the real error, the backup location and a retry. Step 8, D13.
A deferred project looks broken to a user who selected it deliberatelyThe modal names the files holding it up and what to do; the sweep stays silent about the same state. Step 8.
The modal flashes for a fast migration and reads as jankIt only opens on the lazy path, which fires exclusively for projects the sweep did not finish or never saw — never in the normal startup flow.

Deliberately deferred: backup retention — nothing is pruned, ever, by decision rather than omission (D9); a success-path telemetry event, which would measure a population already known (D12); any filesystem scan for unregistered projects (D2 above).

1 · What & why

Since Frame became a read-only overlay it plants no file at a repository's root, so an agent learns that Frame exists at launch — through a wrapper on PATH, or through flags Frame appends to the line it types into the terminal. Every one of those mechanisms is switched off on Windows: launchEnv.supportsWrappers() returns false for win32, and shellSetup.deliveryFor() answers { mode: 'none', reason: 'platform' } before it looks at which shell the lane is running. What is left is the inline branch, which appends a 993-byte, 9-line, 6-backtick preamble to a command typed into the PTY — a POSIX shell swallows that as a quoted continuation, cmd.exe submits at the first newline and PowerShell reads every backtick as an escape. --settings sits at the end of that line and is the first thing lost, and with it the spec-hint hooks: a Windows session loses not just "Frame exists" but the project's recorded memory.

The shape of the fix is smaller than the problem, because of two facts the spec surfaced and this pass verified. First, the payload is already correct on Windows — prepareLaunchAssets gates only its wrapper line on the platform, so a Frame project on Windows today already holds a byte-correct preamble-claude.txt and claude-settings.json. What is missing is not a mechanism but a carrier. Second, Claude Code accepts --append-system-prompt-file, a path where --append-system-prompt takes a string. Both arguments become plain paths, the typed line becomes single-line, and newlines, backticks and quote nesting stop existing rather than being escaped around. Three independent carriers follow: the composed launch passes paths; .frame/bin finally joins the Windows PATH; and a claude.cmd plus a PowerShell init file catch a launch the user types by hand.

Architectural notes
  • Nothing with a newline reaches the PTY: the value of every flag is a path. The 993-byte string never appears on a command line, so terminalManager.js:736's command + '\r' carries one line by construction, not by escaping.
  • Project-relative, forward slashes: a lane's cwd is its project, Windows file APIs accept /, and a relative path dodges both the \ escaping that breaks in a POSIX shell and any question about spaces in the project path — so the same line runs in cmd, powershell, pwsh and Git Bash.
  • POSIX is not made to depend on it: the file flag is chosen only where supportsWrappers(platform) is false. macOS and Linux keep the wrapper and the string flag they have today, so a version-dependent flag never lands on a path that currently works.
  • Independent of the wrapper: this line is composed whether or not claude.cmd was written, which is what lets goal 1 ship on its own.

Architectural notes
  • Finding the real CLI without finding itself: for /f … in ('where claude') walks every hit in PATH order and skips any whose %%~dpI equals %~dp0 — the batch equivalent of the POSIX wrapper's path_without_self, resolved at run time so a version-manager switch is picked up rather than baked in.
  • A wrapper that cannot run is worse than no wrapper: with nothing left after the self-exclusion, the script prints Frame: claude was not found on PATH. and exits 127, shadowing nothing. FRAME_NO_WRAP=1 executes the real CLI with no Frame arguments — the same escape hatch, honoured in the same one place.
  • Exit codes survive: every branch jumps to one pass-through label ending in a bare exit /b. exit /b %ERRORLEVEL% inside an if (…) block would report the code from before the call, because cmd.exe expands variables when it parses the whole block.
  • A tool earns a .cmd by having a file-taking flag: the rule is injection.promptFileFlag, not a hardcoded tool name. Codex and Gemini have no equivalent, so they get no wrapper and behave on Windows exactly as they do today.

Architectural notes
  • ptyManager needs no change: createTerminal already appends a mode: 'flag' delivery's args to shellArgs, and the Windows branch leaves shellArgs empty — so a PowerShell delivery lands as spawn arguments with nothing typed into the terminal. That also dissolves the recorded IN-FLIGHT collision with audit-q3-performance-resources.
  • Execution policy, scoped: Windows clients default to Restricted, which blocks dot-sourcing an unsigned local .ps1. -ExecutionPolicy Bypass lifts it for this one process — nothing machine-wide, the same bargain launchEnv already makes for PATH.
  • Why a family table rather than a platform check: bash.exe resolves to family posix, so without initFamilies a Git Bash lane would be handed an init.sh defining functions that point at wrappers Windows does not write. The table is the thing that says "deliverable here", and it keeps init.ps1 from ever being offered to a Mac.
  • No retry, by construction: onSetupTimeout only retries mode: 'type'. A spawn flag cannot be re-sent, which is already true for fish and is correct here for the same reason.

3 · Decision story

Business decisions

D1 · Should a Windows lane Frame cannot set up say so?
chosen
Stay silent
No new UI, consistent with macOS — but a user in cmd.exe never learns why their agent seems less informed.
A quiet note on the lane card
Discoverable and honest — but renderer work in the one area with no test harness, and a row that is always present stops being read.
Why: unsupported keeps meaning "nothing was sent, nothing is shown", exactly as it does for nu on macOS today; after this spec that state belongs to cmd.exe, Git Bash and WSL. The lane works — it simply carries no Frame context. failed stays the only state with a card row, which is what a PowerShell lane whose init could not be sourced will correctly report.
D2 · What happens when an older Claude Code rejects --append-system-prompt-file?
chosen
Auto-retry bare, with a notice
Costs one gate widening in src/renderer/agentDispatch.js, an area with no tests — and gives every platform the honest fallback.
No fallback — let it fail loudly
Simpler, and treats the flag as a hard requirement — but the user meets a dead lane and a cryptic CLI error instead of a working agent.
Why: an unknown option is fatal, verified against the shipping CLI. Without a fallback, a stale Windows install would go from broken context to broken launch — strictly worse than the problem being fixed. The relaunch mechanism already exists for --permission-mode auto; only its gate needed widening from the caller's own flags to the composed set.

Technical decisions

D3 · What carries the composed launch on Windows?
chosen
Bare CLI name + two project-relative path flags
One line every Windows shell runs, works with or without the wrapper — but it means the wrapper must defer rather than compose, to keep a single injection route.
Route through the wrapper, per shell
Mirrors the POSIX design exactly — but needs the lane's shell threaded into getLaunchCommand, and still leaves Git Bash with no answer.
Why: no wrapper path is shell-agnostic — ./.frame/bin/claude.cmd reads as a switch to cmd.exe, and .\.frame\bin\claude.cmd has its backslashes eaten by Git Bash. A bare name plus relative paths is the only single line all four shells accept, and it keeps goal 1 independent of goal 2.
D4 · How does PowerShell receive its init?
chosen
-ExecutionPolicy Bypass -NoExit -Command ". 'init.ps1'; <marker>"
Keeps the file-based shape the POSIX and fish lanes use and leaves something to paste by hand — but Group Policy can still override the flag on a locked-down machine.
Inline the definitions in -Command, no file
Immune to execution policy entirely — but a long generated string inside an argv node-pty must re-quote for ConPTY, with nothing to read or re-run when it fails.
Why: Windows clients default to Restricted, which blocks dot-sourcing an unsigned local .ps1. The flag lifts it for one process and touches nothing machine-wide — the same bargain launchEnv already makes for PATH. Where Group Policy wins, the marker never arrives and the lane reports failed: the designed path, not a new failure mode.
D5 · Should this spec's work ship with tests?
chosen
Pure logic and data transforms only
Windows behaviour asserted from a Mac, because platform is a parameter — but the generated batch and PowerShell are checked as strings, not executed.
Everything testable
Would also execute claude.cmd and init.ps1 under { skip: !win32 } — genuinely stronger, but those assertions run only on the new CI leg and never on a developer's machine.
Why: this is the convention the testing record describes — target the pure module, skip its Electron-coupled wrapper — and the answer terminal-session-setup gave for the same area. Re-verified this pass: src/renderer/ still has no DOM harness, with no jsdom, playwright, @testing-library or puppeteer in devDependencies.
D6 · Which tools get a Windows wrapper? decided silently
chosen
Any tool whose injection record has promptFileFlag
A condition rather than a special case — Codex and Gemini fall out naturally, and a future tool that gains such a flag is covered without editing this rule.
A hardcoded "claude only" branch
Shorter to write — but states the tool instead of the reason, and would have to be revisited by whoever picks up Codex.
Why: the file-taking flag is precisely what lets the batch file stay plain — it passes paths, never a 993-byte preamble. A tool without one would need the prose embedded in a generated script, which is the problem this spec exists to remove.
D7 · How do the two injection routes avoid stacking? follows from D3
chosen
The .cmd defers when the flag is already in %*
Whoever composed first owns the injection — one extra process hop when a dispatch resolves through the wrapper.
Accept a duplicate flag pair
Last-wins would be harmless in practice since both point at the same files — but it contradicts the constraint outright and would rot the moment the two disagree.
Why: D3 makes the composed line resolve through .frame/bin on PATH, so both routes can be live at once. Reading its own arguments is how the wrapper knows which case it is in — the same "one path, not two guarded ones" rule terminal-context-boundary established, restated for a shell that resolves by extension.
D8 · How does the .cmd propagate the child's exit code? follows from D3
chosen
One goto pass-through label ending in bare exit /b
Slightly more label plumbing than inline exits — and the only form that is actually correct.
exit /b %ERRORLEVEL% after each call
Reads more explicitly — but inside an if (…) block cmd.exe expands the variable when it parses the block, so it reports the code from before the call.
Why: success criterion S5 is "the child's exit code reaches the shell unchanged", and the naive form silently fails it in exactly the branches that matter. A bare exit /b leaves the errorlevel the call set.
D9 · Does ptyManager change for the PowerShell lane? follows from D4
chosen
No — the existing mode: 'flag' path already carries it
Zero new code, and the file leaves this spec's footprint entirely.
Add a Windows branch to createTerminal
More explicit about what Windows does — but duplicates a path that already works and collides with an in-flight spec.
Why: createTerminal appends a flag delivery's args to shellArgs unconditionally, and the Windows branch leaves shellArgs empty — so PowerShell's setup lands as spawn arguments with nothing typed. As a consequence the recorded IN-FLIGHT collision with audit-q3-performance-resources on ptyManager.js disappears rather than needing to be scheduled around.
D10 · How does npm test run on Windows? follows from D5
chosen
A repo-local scripts/run-tests.js launcher
One more file to maintain — but it makes the fixtures/ exclusion explicit instead of a property of the shell that happened to expand the glob.
A cross-env-style dependency
The conventional answer — but CI deliberately runs no npm ci, so anything in node_modules passes locally and fails in CI by design.
Why: FRAME_ACTIVITY_HOME=… node --test test/*.test.js is POSIX-only twice over: cmd.exe sets no inline environment variable, and neither cmd nor Node 20 expands the glob. Success criterion S7 is unreachable without replacing the invocation, and the no-npm ci rule fixes which replacements are available.
D11 · Where does the package.json footprint collision go? follows from D10
chosen
Recorded, and the two specs run sequentially
Costs the option of running this spec in a parallel worktree alongside the audit — which is not currently being asked for.
Keep package.json out and run the launcher only in CI
Avoids the collision — but leaves npm test broken on a Windows developer's machine, and S7 names npm test specifically.
Why: audit-q3-performance-resources is phase implementing with package.json in its footprint (T10 in progress, last touched 2026-07-19). This spec changes exactly one line of that file and nothing else in the audit's footprint, so sequencing is enough — but it is recorded rather than discovered at merge time.

4 · Risks & edges

Edge / riskPlan's answer
Claude Code too old to know --append-system-prompt-file. The flag has no --help row of its own — it appears only inside --bare's description — and an unknown option is fatal.D2: the bare relaunch fires on Frame's composed flags, so the session comes up without context and says so. The protocol records the version it was verified against (2.1.237); a hand-typed launch through the .cmd has no such retry, which the protocol states plainly along with FRAME_NO_WRAP=1 as the manual way out.
A space in the project path. Frame projects live under Documents as often as not, and %~dp0 quoting is the classic batch failure.Flow A sidesteps it entirely by staying project-relative. Flow B cannot — the wrapper has to locate the project from wherever it was invoked — so every path in the .cmd is a quoted variable expansion, and the protocol tests it against a real path with a space rather than trusting the reasoning.
Group Policy overrides -ExecutionPolicy Bypass on a managed machine, so init.ps1 cannot be dot-sourced.The marker never arrives, the lane reports failed, and the card offers the manual line — the path terminal-session-setup already built. The manual line would fail for the same reason, which is a real limit and is stated in the protocol rather than papered over. Goals 1–3 are unaffected: the composed launch and PATHEXT resolution do not touch execution policy.
Git Bash resolves PATH with :, but prependFrameBin joins with ; on win32.Correct as written: the value being extended is process.env.PATH, which is already Windows-shaped, and MSYS converts the whole thing at startup. Git Bash gets goal 1 and goal 3; it is excluded from goal 2 (no PATHEXT) and from goal 4 (family posix is not deliverable on win32), both as stated limits.
The rest of the suite has never run on Windows. Several tests shell out to bash, sh or zsh.The precedent already exists — frameTemplates.test.js guards its executed wrappers with { skip: !POSIX }. Step 6 extends that guard to the remaining shell-executing tests and lets the new CI leg be the judge. Git-invoking tests are fine: windows-latest ships git.
writeIfChanged chmods wrappers to 0o755, which is meaningless on Windows.writeWrapper passes no mode for the cmd family. A .cmd is executable by extension, and Node's chmod on Windows only carries the read-only bit.
A Windows lane reporting unsupported looks identical to a working one.Accepted, by D1. It is the same trade macOS already makes for nu, and reversing it later is a lane-card change, not an architecture change.
Two --settings values on one line would drop the spec-hint hooks.Unchanged and already handled: takeSettingsFlags merges a caller's payload into the file Frame writes rather than passing a second flag. The file-flag branch composes from the same merged file.

Deliberately deferred: Codex and Gemini on Windows (no equivalent file flag — D6 leaves the door open without opening it); rewriting the POSIX wrapper to use the file flag (its own follow-up, so a version-dependent flag never lands on a path that works today); WSL (a second machine, not a shell — the supported route is running Frame inside WSL); a hand-typed claude in Git Bash (would need an extensionless wrapper on Windows and a per-shell carrier choice); cmd.exe function equivalence; Windows packaging and release artifacts.

1 · What & why

Frame does a great deal of work nobody sees, and records none of it. Six filesystem watchers and five visibility-gated pollers fire on their own schedule; reconcilePhase rewrites spec status files with no user gesture behind it; fsSafe quietly restores corrupt state from a .bak. Worse, roughly 2,800 lines of Frame's machinery live in .frame/bin/ and execute in four host processes the app cannot observe at all — the git pre-commit hook, Claude Code's tool hooks, the orchestration bus, and implement-launch.js, which runs with Frame closed entirely.

The cost is that Frame's own guarantees are unfalsifiable. spec-hint.js exits silently on eleven different paths, so "the hook ran and deliberately stayed quiet" is indistinguishable from "the hook never fired" — and the Spec Knowledge Layer's entire claim is that it always fires. The same blindness let a merge-time watcher cascade downgrade eighteen specs' status files with no trace. This plan records the work Frame initiates on its own, and surfaces it in a panel.

The shape follows from one constraint the obvious alternatives fail. An in-process logger module cannot reach half the surface, because half the surface is not in Frame's process — so the sink is a file-append contract that dependency-free scripts can call, not a module. And because a dead watcher emits nothing, silence alone is ambiguous: guards therefore record their suppressions, so the panel can tell "working, nothing needed" from "broken".

Scope is deliberately Tier 1 of three. Repo-mutation records and script version-drift detection (Tier 2) and orchestration/PTY/IPC detail (Tier 3) are named and deferred rather than half-built.

Architectural notes
  • The registry gates the write, not the call site: src/shared/activityEvents.js declares every event, its kind and its field enums, mirroring how telemetryEvents.js governs what may leave the machine. An unregistered event is dropped. This is what stops the drift perfMonitor.js's eight scattered call sites demonstrate.
  • No free-form strings ever reach disk: fields are enum reason codes, counts, durations and project-relative paths. redact() then runs as belt-and-braces on the app side rather than as the only defence — the promptLogger plaintext bug is the anti-pattern.
  • The bucket key comes from the absolute path: promptLogger.js:46 keys prompt history by path.basename today, so two projects both named api share one file. The activity record does not repeat that.
  • Memory first, disk second: the ring buffer always fills, so when something breaks the history is already there. A monitor you must switch on before the bug is nearly useless.

Architectural notes
  • This is the flow that makes the guarantee falsifiable: today all eleven quiet paths exit 0 with no output, so a working hook and an uninstalled hook look identical. Distinct reason codes end that.
  • The never-block contract is unchanged: a failure to append must not write to stdout, must not fail the tool call, and must not fail a commit when the same helper runs under the git pre-commit hook. spec-hint.js already honours this shape; the append helper inherits it.

  • Old copies must not break: .frame/bin/ is refreshed only on init, so a user may run a generation that predates the helper. The require is guarded and the script degrades to today's behaviour.

Architectural notes
  • The watcher watches a file the app itself writes — unguarded, it would retrigger on its own appends. That is precisely the loop class audit-q3-performance-resources T04 solved with self-write stamps in specManager.js; the same pattern is reused rather than reinvented.
  • Concurrency is real here: the app, a git hook and a Claude hook can append at the same moment. Lines stay well under 4 KB so a single O_APPEND write is atomic on POSIX. Windows offers no equivalent guarantee — noted for audit-q3-cross-platform, not solved in this spec.
  • Events written while Frame was closed are not lost: implement-launch.js runs with the app shut down, so the panel reads the file on open rather than trusting the ring buffer alone.
  • The stream must not become the load: pushes are coalesced and back-pressured the way ptyManager.js already handles PTY output (OUTPUT_HIGH_WATER_BYTES, 16 ms flush).

3 · Decision story

Business decisions

D1 · How far back should the activity record reach?
chosen
Size rotation and a time sweep together
2 MB → one generation, plus a 7-day sweep. Two rules instead of one.
Size rotation alone
Firm disk ceiling, but a quiet project keeps months-old noise.
Time window alone
Predictable reach, but disk is unbounded on a busy day.
Why: the two failure modes are independent, so one rule cannot cover both. The 7 days is not a new constant — it reuses STATE_TTL_MS from spec-hint.js:37, which already sweeps session state on the same cadence.
D2 · Should suppressed work appear in the user's default view?
chosen
Visible, but muted
Guard events render dimmed in the labelled view; needs burst aggregation to stay calm.
Detail view only
Quieter default, but it cannot answer "is this still alive?".
Why: a dead watcher and a healthy idle watcher both produce silence. Suppressions are the only thing that separates them, so hiding them behind a toggle would remove the panel's main diagnostic value for the sake of tidiness.
D3 · In which view modes should the right rail appear?
chosen
Every mode, at the app's outer edge
On the board screen it sits outside the board's own .lane-rail, separated by the terminal container's card margin.
Hidden on the board view
Avoids two vertical strips, at the cost of a landmark that disappears.
Why: #terminal-container hosts three modes (multiTerminalUI.js:6) and the board renders its own rail inside it. A rail that moves or vanishes between modes stops being scannable — the reason activity bars sit on the outermost edge. This also corrected the original proposal, which placed the rail between terminal and panel, where every panel toggle would shift it sideways.

Technical decisions

D4 · Where does the record live on disk?
chosen
User scope — ~/.frame/activity/<key>/
Out-of-process scripts must resolve the home directory and derive the key themselves.
In-repo — .frame/runtime/activity/
Zero path resolution for the scripts, but it lands inside the user's working tree.
Why: the decisive fact is that Frame never edits a project's .gitignore, so .frame/runtime/ is not ignored in a user's repository — an in-repo record would dirty their git status on every watcher fire, and would ship to the team the moment anyone opts into committing .frame/. promptLogger.js:34 already keeps churny personal logs under ~/.frame/, so this follows an existing precedent rather than inventing a location.
D5 · Should this spec's work ship with tests?
chosen
Pure logic and data transforms
Covers the append contract, key derivation, rotation, registry validation and label formatting; the panel and rail are verified by hand.
Everything testable, including Electron-coupled modules
Broader evidence, paid for in fragile require-stub maintenance.
None this time
Nothing to maintain, but the sink's correctness would rest on manual checking alone.
Why: this matches the convention already in force per PROJECT_NOTES.md § Testing — target the pure module, skip the Electron-coupled wrapper. The record's Not covered line for src/renderer/ was re-verified rather than trusted: jsdom, playwright, @testing-library/dom, puppeteer, vitest and jest are all absent from package.json, so the panel genuinely has no test path today.
D6 · How can both the app and .frame/bin/ redact secrets without duplicating the patterns? follows from D4
chosen
Extract redact() to scripts/redact.js; logger.js re-exports it
One function moves and joins the shipped parser set; logger.js's public API is unchanged.
Duplicate the patterns inside the append helper
No refactor, but two copies of a security-relevant regex set that will drift apart.
Why: redact() is documented in logger.js as usable from plain node, but .frame/bin/ scripts cannot reach src/main/. Extraction is the only option that leaves exactly one copy. Decided silently — the alternative fails the constraint outright.
D7 · How does the panel learn about appends it did not make? follows from D4
chosen
A watcher on the record, with a self-write stamp
Live updates from foreign processes; requires the stamp to avoid retriggering on the app's own writes.
Re-read the file on a timer
No self-write hazard, but staler and it adds a poller to a codebase that just finished gating them.
Why: the self-write loop is a known, already-solved hazard here — audit-q3-performance-resources T04 added exactly this stamp to specManager.js's watchers. Reusing the pattern is cheaper and more consistent than introducing a seventh polling loop.
D8 · How do suppression bursts stay compatible with a visible default view? follows from D2
chosen
Aggregate the burst into one record
A debounce collapsing 12 fires writes one row carrying collapsed: 12.
Stream each suppression and rely on the rate cap
Simpler producer, but the cap then silently drops events the user was promised.
Why: D2 puts the noisiest event class into the default view, so the noise has to be handled at the source rather than by truncation. Aggregation keeps the count truthful; a rate cap alone would make "12 fires" read as "1".

1 · What & why

Whether a project's Frame context is private to one machine or shared with a team is today a git side effect — .frame/ untracked means a signed block in .git/info/exclude hides it; committing it is the undocumented opt-in. Nothing names the mode, shows it, or lets you choose it, and flipping it naively would commit machine-local junk (orchestration bus, worktrees, generated bin/ scripts). Meanwhile the one genuinely per-project setting Frame has (Spec-Driven Development) sits in the app-wide Settings modal, init silently decides both questions, and three dead flags ship in every new config.

The plan makes the mode an explicit setting: settings.gitSharing: "local" | "repo" in .frame/config.json — which in repo mode travels with the repo for free. Sharing becomes safe by construction via a Frame-owned .frame/.gitignore declaring the machine-local paths (no overlay violation: the file lives inside Frame's own directory). A Project Settings modal, opened from a gear on the project row, owns Spec-Driven, Git Sharing and Remove; App Settings goes back to being app-wide; init asks both questions before the first byte; a dismissible hint makes repo mode discoverable on repos that look shared; one telemetry event makes the choice measurable. Frame never stages, commits, or untracks — transitions are config + exclude-block + gitignore writes only.

3 · Decision story

Business decisions

B1 · What does the project row show for a non-Frame project once × becomes a gear?
chosen
Gear on every row
Non-Frame modal shows only header + Remove; settings sections absent.
Gear only on Frame rows, × stays elsewhere
No near-empty modal, but two different row affordances and the "nervous ×" survives.
Why: one affordance everywhere, and a natural home for future per-project actions (e.g. Initialize). Asked at the gate; user chose the recommended option.
B2 · What are the mode values called — intent names or mechanism names? post-plan
chosen
local / repo (mechanism)
Accurate for every user — including the solo dev committing .frame/ for backup or multi-machine sync — and matches git's own scope vocabulary.
private / team (intent)
Benefit-oriented, but "team" mislabels solo sharing and "private" overpromises in an already-private repo.
Why: the setting's mechanism is the product — it controls exactly whether .frame/ lives in the repository. Mechanism labels stay true in the D3 declared-vs-effective display; a follow-up decision then removed team language from the product surface entirely — the hint button reads "Share in the repository" and the module is sharingHint.js. Raised by the user after planning; renamed before implementation, so no migration needed.

Technical decisions

T1 · Should this spec's work ship with tests?
chosen
Pure logic only
gitSharing, gitExclude mode, template, telemetry event, stubbed init — renderer untested, as all renderer code is today.
Everything testable / none this time
Renderer is unreachable without adopting a DOM harness (out of scope); zero tests would leave acceptance 9's idempotence unproven.
Why: matches the recorded convention (node --test, pure main/shared modules, Electron stubbed where unavoidable — testing record in PROJECT_NOTES.md). Asked at the gate.
T2 · Sharing hint: copy the spec-driven hint pattern, or extract a shared popover module?
chosen
Copy the pattern (standalone sharingHint.js)
~200 duplicated lines; zero risk to the working, untested existing hint.
Extract shared hintPopover.js
Less duplication, but refactors working renderer code with no tests to catch a regression.
Why: the project's core rule is that refactors don't ride along; D7 asks for the same mechanism, not the same code. Asked at the gate.
T3 · Where does the sharing logic live?
chosen
New src/main/gitSharing.js composing gitExclude
Own JSON read-modify-write of config; Electron-free, so directly testable.
Extend gitExclude.js or frameProject.js
Either violates D5 (gitExclude must stay config-ignorant) or buries pure logic in an Electron-coupled module.
Why: D5 forces the direction frameProject → gitSharing → gitExclude; decided silently — only one defensible shape.
T4 · How is the sharing state exposed over IPC?
chosen
Three channels: GET state, SET mode, GET repo signal
GET state works without .frame/ (serves the init modal's isRepo check); signal reads run only when the hint evaluates.
One fat channel returning everything
Simpler surface, but runs git-log author counting on every modal open for data only the hint needs.
Why: both git reads behind the hint are the expensive-ish ones; keeping them behind their own invoke keeps the modal's state read cheap. Silent decision.
T5 · What exactly goes into .frame/.gitignore?
chosen
Spec's table + fsSafe artifacts (*.bak, *.tmp, *.corrupt-*)
Slightly wider than the table's "(+ .bak)", generalized to all crash-safety suffixes.
Table paths only
Repo-mode projects would commit tasks.json.bak / .tmp scratch the first time fsSafe runs.
Why: Frame's own repo already ignores these globally; the spec's "(+ .bak)" names the class. Signed header, unsigned user lines preserved (stripOurs semantics). Silent decision.
T6 · The in-flight footprint collision with audit-q3-performance-resources
chosen
Declare honestly, let the orchestrator serialize
This spec may wait on frameProject.js / index.html until that spec merges.
Carve the shared files out of this footprint
Would hide a real collision from the conductor — the one thing footprints exist to prevent.
Why: collision detection is the orchestrator's job and only works on honest footprints; no content conflict expected (their changes are perf-instrumentation-shaped). Silent decision.
T7 · What happens to the existing spec-driven hint? follows from B1
chosen
Re-anchor to the active row's gear, update copy, behaviour unchanged
Gear is hover-revealed, so it's forced visible while a hint points at it.
Leave it anchored to the app Settings button
Would point at a modal that no longer contains the switch and copy that names a deleted section.
Why: the spec itself says the Project Settings modal is "opened by the project row's gear, and by the spec-driven hint popover"; acceptance 7 pins the behaviour (flag write, dismissal, refresh) as identical. Silent decision.

1 · What & why

Since non-invasive-overlay, Frame plants nothing in a working tree, so an agent learns about Frame only at launch — a preamble of pointers passed as flags to Claude Code, or read from a file by a .frame/bin/<tool> wrapper for Codex and Gemini. The trade was deliberate and it holds. What does not hold is where the boundary falls: the wrapper runs only because Frame types its path, so a user typing claude in Frame's own terminal — the most natural thing in the product — gets nothing. Two sessions in the same window, in the same project, one Frame-aware and one not, with nothing on screen explaining the difference. The rule is also written nowhere, so a user cannot tell a boundary from a bug.

The shape of the fix is to make Frame's own bin directory the first entry on PATH in the terminals Frame spawns, and to give every tool a current wrapper there. The obvious alternatives were rejected for one reason each: a line in the user's shell rc and a pointer block in ~/.claude/CLAUDE.md both write outside .frame/, which is the rule this product is built on; and both are static, so neither can carry a fresh preamble or the spec-hint hooks. An environment variable on a process Frame spawns leaves nothing on disk to undo.

Architectural notes
  • The boundary is the terminal, not the dispatch. That is the whole change: the rule Frame intended and the rule Frame enforced were different, and only the second one was visible to users.
  • Recursion guard: the wrapper is named after the tool it wraps and sits first on PATH, so resolving by name would re-enter itself. It removes its own directory from PATH before resolving — at runtime, so a version-manager switch or a reinstall cannot leave a baked path pointing at a binary that moved.
  • Escape hatch: command claude runs the unwrapped CLI; documented next to the boundary statement rather than left as folklore.

The wrapper, in one look

#!/usr/bin/env bash
# Frame AI Tool Wrapper — generated; rewritten on every project open.
SELF_DIR="$(cd "$(dirname "$0")" && pwd)"
PROJECT_ROOT="$(find_project_root)"          # walks up to the dir holding .frame/
PREAMBLE="$PROJECT_ROOT/.frame/runtime/preamble.txt"
SETTINGS="$PROJECT_ROOT/.frame/runtime/claude-settings.json"

# Resolve the real binary with our own directory out of the way.
CLEAN_PATH="${PATH//$SELF_DIR:/}"
REAL="$(PATH="$CLEAN_PATH" command -v claude)"

if [ -n "$REAL" ] && [ -f "$PREAMBLE" ]; then
  exec "$REAL" --append-system-prompt "$(cat "$PREAMBLE")" --settings "$SETTINGS" "$@"
else
  exec "${REAL:-claude}" "$@"                # half-written .frame/ → bare CLI
fi

3 · Decision story

Business decisions

D1 · Does Windows belong in this spec?
chosen
POSIX now, Windows as its own task
Preserves today's behaviour instead of regressing it; Windows users stay on the wrong side of the boundary until that task lands.
Solve Windows here too
Every user covered, but the spec grows a second wrapper format, a platform-dependent separator, and a verification pass that needs a Windows machine.
Why: Frame's wrapper mechanism is already POSIX-only — .frame/bin/codex is a bash script and ./.frame/bin/codex was never runnable on Windows. Limiting PATH injection to POSIX therefore creates no new gap; it holds the line where it already is.
D2 · Where does the boundary rule get stated?
chosen
App Settings and the REFERENCE template
Reaches both readers; the REFERENCE line only lands in new projects, since only the spec section of that file is managed.
Settings only
One surface, no doc bloat — but an agent launched outside Frame never encounters the rule, which is exactly the session that raises the question.
Why: Two audiences read in two places. The user meets the rule in Settings beside the escape hatch; the agent meets it in .frame/docs/REFERENCE.md, which is already where the preamble points it. Settings covers every existing user immediately, which is what makes the REFERENCE limitation acceptable.
D3 · What happens to src/templates/CLAUDE.md? decided silently
chosen
Delete it
Removes a file that still instructs agents to read root meta files and closes with a note about a symlink Frame no longer plants.
Rewrite as a project-layer template
Would produce a template nothing consumes.
Why: The evidence pass found no code path that reads it — an orphan the overlay left behind. With no consumer, "rewrite" has no defensible form, so this was recorded rather than asked.

Technical decisions

D4 · How does the wrapper find the real binary?
chosen
Resolve at runtime with its own directory stripped from PATH
Survives a version-manager switch or a reinstall; costs a few lines of bash.
Bake the absolute path in at write time
Simpler and deterministic, but goes stale silently when the CLI moves, and stays stale until the next project open.
Why: The wrapper is named after the tool it wraps and sits first on PATH, so resolving by name would re-enter itself. Stripping its own directory removes the recursion and keeps resolution current, which a baked path cannot.
D5 · Does Frame's own dispatch go through the wrapper too? follows from D4
chosen
Yes — one exec path for everything
Collision becomes structurally impossible and the visible command line shortens; it overturns a shipped decision and widens the blast radius of a broken wrapper.
Keep the flag/wrapper split, add a bypass
Honours the prior design and keeps inline preamble composition, but needs a bypass — or a per-tool "already injected" check — that exists only to stop Frame colliding with itself.
Why: non-invasive-overlay split injection per tool, and that split cannot survive PATH injection: the dispatched command resolves to the wrapper and the flag is applied twice. The rejected option answers a self-inflicted collision with a third mechanism; the chosen one removes the second injection path instead. injection.type survives as data — which flags a wrapper emits — rather than as a behavioural switch. Overturning a prior spec's decision is allowed; doing it silently is not, so it is recorded here and will be repeated in outcome.md.
D6 · How is the duplicate --settings fixed?
chosen
Merge the payloads at dispatch
Small and contained; aiToolManager has to recognise a --settings pair inside the extra flags.
Each tool's injection owns its settings
Closes the collision class for good, but changes the contract between specManager and aiToolManager — implement-modes-v2's territory.
Why: An autonomous implement launch passes --settings twice today — once for the spec-hint hooks, once for the permissions — and the last flag most likely wins, so the hooks are lost for exactly the runs that go unattended. Merging is a change in one module; the settings file is regenerated per launch anyway. .frame/bin/implement-launch.js keeps its own single flag, since a launch from outside the app has no preamble or hooks to merge with.
D7 · Does this work ship with tests?
chosen
Everything testable — extract the pure part
PATH composition moves to a pure module so it can be covered; PTY spawning and IPC stay untested, as the record says they must.
Extend the existing pure surface only
Fewer files, but the PATH logic stays inside an Electron-coupled module where no test can reach it.
Why: The testing record's convention is to test the pure module and skip its Electron-coupled wrapper — telemetryEvents/telemetry, activityEvents/activityLog, gitSharing. Extracting launchEnv.js follows the project's own pattern rather than inventing a second one, and wrapper generation is already covered in test/frameTemplates.test.js.

6 · Convergence log

  1. Iteration 1 — two constraints had no owning section (spec-hint hooks staying Claude-only, and the .frame/-only footprint) → both assigned to the resolved-decisions block, with C7 additionally attached to the settings-merge step.
  2. Iteration 2 — wrapper generation and dispatch unification were bundled into overlapping steps → split into mechanism (generate and refresh) and behaviour (dispatch switches to it), each shippable alone.
  3. Iteration 3 — ordering defect: PATH injection placed before dispatch unification would create a build where Frame types claude …, PATH resolves it to the wrapper, and the flags are injected twice → order reversed, and the dispatched command kept as a relative path so no collision window can exist.
  4. Iteration 4 — S8 had no owner, and S10 reappeared under the unified wrapper because the extra flags still append a second --settings → S8 mapped to the pure module's tests plus the existing footprint walk; the merge step redefined to swallow the extra flag pair rather than sit beside it.

1 · What & why

Frame puts .frame/bin first on the PATH of every terminal it spawns, so that typing claude in a Frame lane runs Frame's wrapper — the thing that hands the CLI this project's context. That works right up until the user's own shell disagrees: rc files run after Frame sets the environment, and nvm, Homebrew and pyenv all prepend their own directory. On a normal developer machine .frame/bin lands sixth, behind the very directory npm i -g installs Codex and Gemini into. The guarantee is therefore conditional on where the user happened to install their CLI, and when it loses, it loses silently: the agent starts and simply doesn't know the project.

The fix is to stop competing on ordering. When a lane's shell is ready, Frame loads one generated file from .frame/runtime/shell/ that defines a shell function per tool — and a function is resolved before any PATH search, so the ordering question disappears rather than being won. The function is a router, not a second injection point: it delegates straight to .frame/bin/<tool>, which remains the only thing that composes the preamble and the only thing that honours FRAME_NO_WRAP=1. PATH stays as the base layer underneath, because functions do not reach subshells and PATH does.

The obvious alternative — pointing ZDOTDIR at a directory inside .frame/ and wrapping the user's startup files, which is roughly what VS Code's shell integration does — is ruled out by the overlay principle. It writes nothing, but it reroutes a mechanism that belongs to the user, and it buys terminal features (command decorations, cwd detection) this spec does not want. What Frame does instead is configure the session it creates, verify that the configuration landed, and — when verification fails — say so on the lane and offer a start button that is guaranteed to carry context.

Architectural notes
  • The function beats ordering, it does not fight it: shell function lookup precedes PATH search entirely, so nvm prepending its own bin directory is no longer relevant to which claude runs.
  • The wrapper stays the injection point: each function is <id>() { "$FRAME_BIN/<id>" "$@"; } with a command <id> fallback. Preamble composition and FRAME_NO_WRAP=1 both keep living in exactly one place.
  • The marker is absent from the line that carries it: the tty echoes a typed command before running it, so the token is printed from two adjacent quoted fragments and only exists literally in real output. Without this, the scan matches its own echo and reports success before the shell has done anything.
  • Suppression sits in front of the existing pipeline: buffered chunks never enter ptyManager's coalescing/backpressure path, so the invisibility costs nothing in the steady state.
  • Not a Frame project → nothing at all: the delivery shape resolves to none, no line is sent and no function or variable is defined.

Architectural notes
  • Fail open, always: every exit path flushes the output buffer and the input queue. Losing context is acceptable; losing the terminal is not.
  • The flush is itself the in-lane statement: a user sitting inside a failed lane sees the real source line and whatever error it produced — the failure is legible where it happened, and the card carries the action.
  • One launch path: the button calls the existing _startAgentIn through a thin export. This spec adds no second way to start an agent.
  • Unsupported ≠ failed: nushell, pwsh and cmd resolve to none and report unsupported — no failure row, because nothing was attempted. Windows has no .cmd shims to point at, and that is blocked rather than deferred by choice.

The generated init file, in one look

.frame/runtime/shell/init.sh      # zsh · bash · sh
.frame/runtime/shell/init.fish    # fish

  1. move .frame/bin to the FRONT of PATH   (after the user's rc files ran)
  2. one function per configured tool:
       claude() { [ -x "$FRAME_BIN/claude" ] && "$FRAME_BIN/claude" "$@" || command claude "$@"; }
       codex()  { … }   gemini() { … }   <custom tool>() { … }

delivery, per shell family
  posix  →  { mode: 'type', line: ` . '…/init.sh' && printf '%s\n' '__frame_ready_''<token>'` }
  fish   →  { mode: 'flag', args: ['-C', "source '…/init.fish'; echo …"] }
  other  →  { mode: 'none' }

state pushed to the renderer
  IPC.TERMINAL_CONTEXT_STATE → { terminalId, state: installed|failed|unsupported, ready }

3 · Decision story

Business decisions

D1 · Does the readiness primitive land in this spec, or a separate one?
chosen
Land it here
Satisfies criterion 12, at the cost of touching agentDispatch.js, index.js and multiTerminalUI.js.
Separate spec
Keeps the footprint at the PTY layer, but ships a marker nothing consumes.
Why: Criterion 12 is a success criterion of this spec, and the marker is the only signal that makes it satisfiable. Splitting would leave the spec unable to pass its own checklist by construction, and would leave four fixed delays in place with the thing that replaces them already built.
D2 · Is the lane's context indicator always visible, or only on failure?
chosen
Only on failure
Cards stay quiet; the one state the user must act on is the only one that appears.
Always visible
States the boundary continuously, at the price of a permanent chip that almost always reads the same.
Why: An indicator that reads "installed" on every card, every time, trains the eye to skip it — and then it is missing precisely when it changes. The boundary is already stated once, permanently, in the Terminal section of Settings that terminal-context-boundary added; the lane card is for the exception.
D3 · Is the off switch global or per project?
chosen
Neither — no off switch
One behaviour to reason about and test; success criterion 10 is dropped, explicitly and on the record.
A setting, global or per project
Gives an escape from the feature as a whole, and a second reason a lane might behave differently from its neighbour.
Why: The user's call at the gate: this is product behaviour, not a preference. What remains is still an out: FRAME_NO_WRAP=1 escapes any single run (unchanged), and a shell where setup cannot be delivered degrades to exactly the PATH-only behaviour the previous spec shipped — the difference is that it is a fact about the shell, not a switch.

Technical decisions

D4 · What happens to keystrokes typed during the invisible setup window?
chosen
Hold in main, flush in order
One queue and a flush ordering to get right; keystrokes survive the window intact.
Pass straight through
No queue at all, but the echo lands in a buffer that is discarded — fast typing reads as dropped characters.
Why: The window is well under a second on a warm shell, so holding costs almost nothing; passing through would make the user watch their own typing disappear, which is a worse bug than the one this spec fixes.
D5 · Should this spec's work ship with tests?
chosen
Pure logic only
shellSetup.js and the init template are covered; the PTY wiring and lane UI are not.
Everything testable — add executed shell cases
Would prove function-over-PATH end to end, at the cost of spawning real shells in the suite.
Why: Matches the convention the testing record describes — target the pure module, skip its Electron-coupled wrapper — and src/renderer/ has no DOM harness to reach the lane card with in the first place.
D6 · How is setup delivered per shell family? decided silently
chosen
Type for zsh/bash/sh, -C flag for fish, nothing for the rest
Two generated files and one inert branch; nushell/pwsh/cmd lanes get the PATH base layer only.
Wrap the user's startup files (ZDOTDIR, --rcfile)
Would win the ordering for every POSIX shell without typing anything — by rerouting a mechanism that belongs to the user.
Why: Constraint 1 rules out startup-file wrapping explicitly, and not because it writes anything. Typing is therefore the only delivery left for zsh and bash, and the invisibility requirement is what pays for it. Windows shells are blocked upstream anyway: there are no .cmd shims for them to point at.
D7 · Where does verification live? decided silently
chosen
Main process, in front of ptyManager's output pipeline
Buffering logic sits in an already-busy module; suppression is genuinely total.
Renderer, scanning the xterm buffer
Keeps ptyManager untouched, but the output has already been rendered by the time it can be recognised.
Why: "None of it is rendered" cannot be satisfied downstream of rendering. ptyManager already owns coalescing and backpressure, so the buffer belongs in front of the same pipeline rather than in a second one.
D8 · Does src/main/pty.js get setup too? decided silently
chosen
No — leave the legacy single-PTY path alone
One implementation to maintain; a path nothing spawns keeps PATH-only behaviour.
Mirror the work into pty.js
Symmetric, but duplicates the buffering machinery into code no renderer flow reaches.
Why: terminal.startTerminal() is a no-op and every lane — board, dispatch, startAiSession — is created through ptyManager. Mirroring would add untested code by construction, and it would widen the footprint into a file another spec is still finishing in.

4 · Risks & edges

Edge / riskPlan's answer
The typed setup line is echoed by the tty before it runs, so a marker scan could match its own echo and confirm a setup that never happened.The delivered line prints the token from two adjacent quoted fragments, so the literal marker exists only in real output. Asserted as an invariant in test/shellSetup.test.js.
A login shell that prints a lot (motd, fastfetch, a slow prompt framework) could grow the suppression buffer without bound.The buffer is capped; exceeding the cap is treated as a timeout — flush, retry once, then failed. A noisy shell costs context, never memory.
The user types during the setup window.Input is queued in writeToTerminal and written through in order the moment setup resolves (D4).
Setup fails while the user is inside the lane, where the board card is not visible.The timeout flush puts the real source line and its error on screen, so the failure is legible in place; the card carries the one-click recovery for when they return to the board.
The source line lands in the user's shell history.Accepted, and reduced: the line is sent with a leading space, which suppresses history under the common ignorespace/HIST_IGNORE_SPACE settings. The line is inert and points only at the project's own file.
A function shadows a tool whose wrapper is missing — .frame/bin/codex is genuinely absent in this checkout, for instance.Each function tests -x "$FRAME_BIN/<id>" and falls back to command <id>, which bypasses the function and cannot recurse. Wrappers are also regenerated on every project open.
Custom tools added after the lane opened have no function in it.The init file is regenerated with the launch assets, so the next lane has it. Within a live lane, the PATH base layer still resolves the wrapper.
A subshell started inside a lane does not inherit shell functions.Unchanged and deliberate: .frame/bin stays first on the exported PATH, which is what subshells inherit.
src/main/ptyManager.js, laneBoard.js and index.js sit in the footprint of audit-q3-performance-resources, still marked implementing.Nine of its ten tasks are complete and the tenth is a measurement pass, not a code change — its coalescing and backpressure work is already in the tree and this plan builds on top of it rather than beside it. pty.js was dropped from the footprint (D8), which removes one overlap outright.
With no off switch, a user who dislikes the behaviour has no global escape.FRAME_NO_WRAP=1 escapes any single run and is untouched; an unsupported shell is a full escape by choice of shell. Recorded as the accepted consequence of D3.

Deliberately deferred: Windows .cmd shims (their own spec — without them Windows lanes have nothing to point at, from any path); nushell setup (no generated file matches its function/PATH model); tmux, ssh and any session Frame did not spawn (the manual one-liner and the lane's Start button cover them); terminal UX features such as command decorations and cwd detection (what startup-file wrapping would buy, and what this spec declines to pay for).

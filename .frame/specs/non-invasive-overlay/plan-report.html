1 · What & why

Frame today mutates every repository it manages: five root files, an existing CLAUDE.md destructively consumed into a symlink, a hook appended to tracked .husky/pre-commit on husky projects, and spec-hint hooks merged into the project's .claude/settings.json. That makes Frame unusable on any codebase the developer doesn't own. This plan turns Frame into a read-only overlay: everything project-specific lives under .frame/, Frame's own generic instructions live once in user-scoped storage (userData/frame-global/), and the AI tool learns about all layers through a short pointer preamble composed at launch time — never by planting files.

Why this shape: pointer-based launch composition is the only design that (a) leaves every repo file byte-identical, (b) kills the per-project template-copy drift that docsManagedBlock exists to chase, and (c) leaves a seam — the new frameStore data-not-paths storage module — through which a future Frame-owned store becomes a backend swap with zero caller changes.

Architectural notes
  • Read-only discovery: instructionDiscovery.js holds zero write calls; the test asserts checksums of scanned files before/after. Debounced fs.watch re-reads on change (specManager pattern).
  • Exclude is worktree-safe: the exclude file is resolved via git rev-parse --git-path info/exclude, never a hardcoded .git/info/exclude join — orchestration worktrees share the common dir.
  • Conditional, self-healing: the signed line is managed on every open. Tracked .frame/ → line removed, so post-opt-in files stay visible on every clone; untracked → line present, so zero-touch holds.

Architectural notes
  • Pointers, never content: the preamble references paths only — nothing goes stale, no duplicate context, and the layers can later move out of the working tree without touching injection logic.
  • Composition is main-side: renderer call sites (index.js:724, agentDispatch.js:277) switch from bare getStartCommand() to one awaited IPC call; quoting via existing quoteArg/composeLaunchCommand.

  • Per-tool config stays declarative: AI_TOOLS.<id>.injection = {type: 'flag'|'wrapper'} — no tool conditionals leak outside aiToolManager (spec constraint).

The storage seam — and the Frame-owned store it prepares for

The future store (per-user/per-project keyed, where team sharing gets solved properly) is a separate, later spec — nothing of it is built here. What this plan builds is the seam that makes it a backend swap instead of a second refactor: every caller speaks data, only frameStore knows where data lives.

The injected preamble, in one look

This project is managed by Frame (overlay mode).
Frame meta-workflow instructions: <userData>/frame-global/AGENTS.md (read first)
Project-specific Frame context:   .frame/AGENTS.md            (if present)
Repo's own instruction files:     CLAUDE.md, .cursorrules, …  (read as usual)
Precedence: the repo owns code conventions; Frame owns the meta-workflow
(tasks, notes, specs, structure). Do not copy content between these files.

D9 · Exclude entry lifecycle silent
chosen
Conditional signed line, reconciled on every open

Write once at init and never revisit
Simpler, but after team opt-in it silently hides every new .frame/ file — silent drift.
Why: Spec Goal 7 (added during review): an exclude that outlives opt-in is the trap, not the feature.
D10 · Seed .frame/AGENTS.md at init? silent
chosen
No — absent until there is project-specific content
Absent is a valid state per Goal 3; the global layer stands alone.
Seed a stub at init
Gives a place to write, but reintroduces a per-project copy of near-generic content.
Why: The whole point of the global layer is not stamping generic content into projects; a stub would be exactly that.
D11 · scripts/ reading STRUCTURE.json — hard cut or fallback? silent
chosen
.frame/ first, root fallback
Frame's own repo stays embedded until embedded-migration runs; scripts serve both layouts read-side.
Hard cut to .frame/ only
Purer, but breaks Frame's own repo and every unmigrated project the day it ships.
Why: Release-coupling reality. The "single model" constraint governs Frame's writes toward new projects; a read fallback in copied scripts is compatibility, not a toggle.
